# Stage 12: demand-driven wet counters and adaptive dry chunks

The implementation is in `src/media/gpu/stepfull.mjs`, `stepfull.wgsl`,
`fast-dry-chunk.mjs`, and `worker.mjs` in this checkout (there is no
`src/gpu/sheet-gpu.mjs`).

- Every simulation step still rebuilds the exact sparse wet frontier. Removing
  that operation loses wet tiles from subsequent steps.
- Ordinary unobserved steps use `wetfrontier`, which omits maximum-water and
  termination-counter reductions. A requested chunk result uses the original
  combined `wetscan` on its last step. Arbitrary counter requests lazily measure
  once with `wetmeasure`; repeated reads reuse it. Capacity, fix, and surface-level
  reads do not request wet measurements.
- Fast drys probe at 50 steps, then use 150 or 200 for sustained wet batches.
  The quiet-film dt boost retains 50-step observations. Full-mode scheduling and
  explicit `GPU_FAST_DRY_CHUNK=50|200` overrides remain supported.
- All chunks respect dry limits and watched checkpoints. Successful termination
  still requires measured dryness or the existing analytically certified tail;
  no epsilon or wet-limit check is relaxed. Coarser observations can execute
  additional iterations, which are included in actual iteration telemetry.

The required frontier pass still runs each step: reducing `wetscan` dispatches
is not an equivalent reduction in total dispatches.

**The requested material wall-time improvement and 3–4x reduction in total
painting counter reads were not achieved.** Combined warm time is effectively
flat (117.98s before, 117.94s after), and general-540 is slightly slower in this
single paired measurement. Most drys terminate after one fast chunk; the
leveling reads and one necessary final observation per call dominate their
read counts. Larger first chunks added redundant iterations, so the default
retains an initial 50-step probe. Sustained long drys can amortize later maps,
but these two workloads do not demonstrate that benefit. Counter-read wait
also includes preceding queued GPU work, not just `mapAsync` overhead.

No painting configuration, image-specific rule, wet threshold, or termination
check was changed. Further substantial readback reduction requires changing
where the leveling/dry decisions execute, rather than only their chunk size.
